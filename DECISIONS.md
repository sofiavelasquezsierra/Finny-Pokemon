## 1. Approve esbuild's build script for pnpm 11

- **Decision:** Added `pnpm-workspace.yaml` with `allowBuilds: { esbuild: true }`, generated by `pnpm approve-builds esbuild`.
- **Why:** The starter pins `pnpm@11.2.1`, but its esbuild approval lives in the `package.json` `"pnpm"` field and in `.npmrc`, which pnpm 11 no longer reads. pnpm 11 treats an unapproved build script as an install error, and every `pnpm <script>` runs an install check first, so `pnpm dev`, `pnpm types` and `pnpm lint` all failed on a clean install. This moves the starter's existing intent to the location pnpm 11 reads.
- **Alternative rejected:** Downgrading the `packageManager` pin to pnpm 10, which overrides the starter's choice to suit my environment. Denying the script (`!esbuild`) also works, but it contradicts the author's stated intent for no gain.
- **Tradeoff accepted:** One extra config file. The old `"pnpm"` field and `.npmrc` entry are left in place, so pnpm 11 still warns that they're ignored.
- **With more time:** Remove the dead config so the install output is clean, and fix the README's "Node.js 18+" (Vite 8 needs `^20.19.0 || >=22.12.0`).
- **Update:** Adding `@tanstack/react-query` made pnpm 11 re-resolve the lockfile, and it dropped `esbuild` and `tsx`. They are *optional* peer dependencies of Vite 8 that the starter's older lockfile had installed. A clean `--frozen-lockfile` install, build, types and lint all pass without them (Vite 8 builds with Rolldown). The `allowBuilds` entry is now inert. I kept it as insurance: if anything pulls esbuild back in, installs would otherwise fail again the same way.

## 2. Cards flip on click to reveal details

- **Decision:** Clicking or tapping a card flips it. The front shows the image, name and types; the back shows the description, the six stats as bars, and height, weight and generation. Each card flips on its own (the flip state lives in the card). The toggle is a `<button aria-expanded>`, the hidden face is `inert`, and under `prefers-reduced-motion` the rotation becomes a crossfade.
- **Why:** The README requires "click to expand/collapse individual cards" and invites creativity, since the designs are "a guide". A flip gives the grid some personality without changing card size, so the rows never shift. `click` covers mouse, tap and keyboard (Enter/Space) with one handler.
- **Alternative rejected:** Hover to flip. It contradicts the README's "click", doesn't exist on touch screens, and to work for keyboard users it would need focus handling plus WCAG 1.4.13 (content on hover must be dismissible, hoverable and persistent). It would also flip every card the pointer crosses while scrolling. Inline expand was the most literal option (the design shows a taller card) and stays the fallback. Spanning 2 columns makes the rest of the grid jump, and `grid-auto-flow: dense` breaks the match between DOM order and visual order.
- **Tradeoff accepted:** The back face must fit the front's size, so the details are a curated subset, and the cards may need to grow (fewer columns than the 5 in the design). There's more accessibility work: `inert` on the hidden face and a reduced-motion fallback.
- **With more time:** User-test whether people find the flip affordance without a hint. Consider a small "details" icon on the front as a visual cue.

## 3. TanStack Query `useInfiniteQuery` for data fetching

- **Decision:** Fetch through `useInfiniteQuery`, keyed by `['pokemon', search]`, with `getNextPageParam` reading `pagination.hasNext`. Infinite scroll is triggered by a small custom `useIntersectionObserver` hook on a sentinel element. The debounce is a small custom `useDebouncedValue` hook.
- **Why:** It handles the server-state problems interviewers probe, by design. Stale responses can't overwrite newer ones, because each search term has its own cache entry. Superseded requests are aborted through the `AbortSignal` it passes in. Next-page requests are deduplicated while one is in flight. It provides loading, error and retry state. One well-known dependency replaces about 70 lines of error-prone reducer, abort and race-guard code.
- **Alternative rejected:** A hand-rolled hook (`useReducer` + `AbortController` + request-ID guard). It has no dependency and shows the fundamentals, but it's exactly where subtle bugs live: StrictMode running effects twice, aborts surfacing as errors, the sentinel firing during a reset. `react-intersection-observer` was also rejected: about 15 lines doesn't justify a dependency.
- **Tradeoff accepted:** About 13 kB gzipped plus a `QueryClientProvider`. I need to be able to explain query keys, `getNextPageParam` and `staleTime`, and describe how I'd do it without the library.
- **With more time:** Prefetch the next page before the sentinel is visible (a larger `rootMargin` already gets most of this). Add a test for the race using a mocked fetch.

## 4. Search UX

- **Decision:** A 300ms debounce on the trimmed input. `keepPreviousData` keeps old results visible and dimmed (`aria-busy`) while new ones load. `?search=` is read on load and written with `history.replaceState`. The empty state offers "Clear search", which also returns focus to the input. If the first page fails, an error block with "Try again" (`refetch`) replaces the grid; if a later page fails, an inline retry appears and the loaded cards are kept. A polite live region announces "N creatures found". The input is `type="search"` with a visually hidden `<label>`.
- **Why:** 300ms balances responsiveness against request volume. Keeping the previous data avoids the grid flickering to skeletons on every keystroke. With `replaceState`, the URL can be shared without filling the back-button history with keystrokes. Every non-happy state gives the user an action. The live region and the label cover screen-reader feedback and WCAG 1.3.1 / 3.3.2.
- **Alternative rejected:** `useDeferredValue` defers rendering but doesn't reduce requests. `pushState` would add a history entry per keystroke. React Router is a whole dependency for one query parameter. Replacing everything with skeletons on each search flickers. Wiping loaded pages when a later page fails throws away the user's progress.
- **Tradeoff accepted:** For about 300ms after typing stops, the results shown don't match the input (they're dimmed to signal that). URL sync covers only `search`, not scroll position or which cards are flipped.
- **With more time:** Restore scroll position on back navigation. Highlight the matched text in the results.

## 5. Deploy to Render as a Node server, early

- **Decision:** Add a small `server/index.ts` that mounts the existing `app` and serves `dist/` statically. Bundle it with `vite build --ssr server/index.ts --outDir dist-server`, run it with `node dist-server/index.js`, and host on Render. Deploy a bare-bones version right after the shell, so every later push redeploys.
- **Why:** The API only exists inside the Vite dev server (`configureServer`), so a static host can't serve it. A live link lets reviewers try the app without cloning. Bundling with Vite needs no new dependency and reuses its handling of the JSON import and the `@/` alias (`.gitignore` already lists `/dist-server`). Deploying early surfaces build and hosting problems on day one, not at the deadline. It also makes the README's `server/index.ts` real.
- **Alternative rejected:** Repo only, which is the minimum deliverable but has no live link. Vercel, which would mean rewriting the server as a serverless function plus `vercel.json`, all platform-specific. `tsx` at runtime, which adds a dependency and compiles on every cold start. Node's native TypeScript support, which would require editing the starter's `app.ts` (the JSON import attribute and extensionless imports).
- **Tradeoff accepted:** About 1h, paid for by moving tests to "with more time". Render's free tier sleeps when idle, so the first load is slow (documented in the README). The deploy depends on a third-party account.
- **With more time:** Tests (Vitest + Testing Library on the card's flip and the search race). A health-check endpoint. Cache headers for the hashed assets.

## 6. No virtualization

- **Decision:** Render every loaded card. Don't virtualize.
- **Why:** The dataset tops out at 1000 records (50 pages of 20). Cards are light DOM, and images are lazy-loaded and resized, so the cost doesn't justify the complexity.
- **Alternative rejected:** TanStack Virtual, which adds a dependency, complicates keyboard focus and Ctrl+F (find in page), and needs row measurement for a responsive grid.
- **Tradeoff accepted:** DOM size grows with scroll depth. That's fine at 1000 records but wouldn't be at 10k+.
- **With more time / at scale:** Virtualize rows with TanStack Virtual. The fixed-size flip cards make row heights predictable, which simplifies it.

## 7. Static dark theme, black background token, `sr-only` h1

- **Decision:** Set `class="dark"` on `<html>` in `index.html`. Change the `.dark` `--background` token to pure black and add `color-scheme: dark`. `App` renders a centred `<main>` (`max-w-6xl px-4`) with a visually hidden `<h1>Pokemon Explorer</h1>`. The page title is now "Pokemon Explorer".
- **Why:** The design is dark only, so setting the class statically in HTML avoids a light-theme flash and any toggle logic. Changing the token (instead of `bg-black` on `<body>`) keeps one source of truth for every `bg-background`. `color-scheme` makes native UI (scrollbars, the search clear button, autofill) match the theme. The `sr-only` h1 matches the design, which has no visible title, while still giving screen-reader users a top-level heading to navigate by.
- **Alternative rejected:** A light/dark toggle, which isn't asked for. Hard-coding `bg-black`, which bypasses the token system. A visible title, which drifts from the design. No h1, which leaves no heading structure.
- **Tradeoff accepted:** Users who prefer a light theme get dark anyway. Sighted users see no page title.
- **With more time:** Honour `prefers-color-scheme` with a light theme that passes contrast checks.
- **Implementation note (#5):** `server/index.ts` creates a new Express app, mounts the existing `app`, then serves `dist/` with `express.static`. It doesn't mutate the imported `app`, which the dev middleware shares. `dist` is resolved from `import.meta.url` rather than the working directory, so `node dist-server/index.js` works from any directory. `pnpm build` now also bundles the server, and `pnpm start` runs it. Known wart: the SSR build also copies `public/` into `dist-server/`. That's harmless (three unused starter SVGs) and would need a function-form `vite.config` to suppress, which isn't worth it.

## 8. Query defaults and the pagination guard

- **Decision:** The `QueryClient` defaults are `staleTime: Infinity`, `refetchOnWindowFocus: false` and `retry: 1`. `getNextPageParam` returns the next page only when `hasNext && data.length > 0`. `fetchPokemonPage` throws on `!res.ok`, and the response is cast to `PokemonPage` without runtime validation. `@tanstack/react-query` is pinned exactly (`5.104.5`) to match the starter's exact pins.
- **Why:** The data is a static fixture, and refetching an infinite query refetches every loaded page in sequence (30 pages scrolled means 30 requests on tab focus). The default 3 retries with exponential backoff delay the error state by about 7s, and the UI offers a manual retry. The server can report `hasNext: true` on an empty page, which would make the sentinel fetch forever. `fetch` resolves on HTTP 500, so TanStack Query would otherwise see a failure as success.
- **Alternative rejected:** The library defaults (stale immediately, refetch on focus, 3 retries). Zod validation of the response, which is a dependency to guard our own fixture server.
- **Tradeoff accepted:** If the data ever became live, it would never refresh without a reload. Malformed responses aren't caught at the boundary.
- **With more time:** Validate the response with a schema if the API weren't ours. A sensible finite `staleTime` if the data became live.
- **Note:** `lastPage` is annotated as `PokemonPage` because TypeScript infers generics left to right through the object literal, and the alphabetical key order puts `getNextPageParam` before `queryFn`.

## 9. Hand-written hooks for debounce, intersection and URL sync

- **Decision:** Three small hooks, with no libraries. `useDebouncedValue` uses `setTimeout` with cleanup. `useIntersectionObserver` returns a **callback ref** plus `isIntersecting` state, and disconnects through React 19's ref cleanup. `readUrlSearchParam` and `useSyncUrlSearchParam` read once and then mirror the value with `history.replaceState`.
- **Why:** Each is under 25 lines and easy to explain. `isIntersecting` is state rather than a fire-once callback, so the grid can keep loading while the sentinel *stays* visible: IntersectionObserver only fires on changes, so a tall screen would otherwise stall after page 2. A callback ref re-attaches the observer when the sentinel mounts conditionally, which `useRef` + `useEffect([])` would miss. `rootMargin` is a string parameter rather than an options object, so the ref's dependencies stay stable and the observer isn't recreated every render.
- **Alternative rejected:** `use-debounce` and `react-intersection-observer` (dependencies for about 10 lines each). React Router or `nuqs` for one query parameter. `pushState`, which adds history spam.
- **Tradeoff accepted:** No `threshold` or `root` options. URL sync is one-way after load, which is fine since `replaceState` never creates entries the back button could return to.
- **With more time:** Unit-test `useDebouncedValue` with fake timers.

## 10. Grid wiring: load-more guards, sentinel, search landmark

- **Decision:** `PokemonGrid` keeps the raw input in state (lazily initialised from `?search=`), debounces the trimmed value, mirrors it to the URL, and flattens `data.pages`. An effect calls `fetchNextPage` only when `isIntersecting && hasNextPage && !isFetching && !isPlaceholderData && !isFetchNextPageError`. The sentinel is a 1px `aria-hidden` div that is always rendered. The input is inside a `<search>` landmark with an `sr-only` `<label>`. The grid is `<ul role="list">` keyed by `id`.
- **Why:** With `keepPreviousData`, `hasNextPage` can describe the *previous* search, so without `!isPlaceholderData` a visible sentinel would page the new query before its first page exists. `!isFetching` covers both the first page and next pages. The error guard stops retry loops; the user retries manually. An always-rendered sentinel avoids a stale `isIntersecting: true` left over from unmounting. `<search>` gives a landmark without a `<form>`'s submit-on-Enter page reload. `role="list"` restores list semantics that Safari/VoiceOver drops under `list-style: none`.
- **Alternative rejected:** Conditionally rendering the sentinel only while `hasNextPage` (stale-state risk). `<form role="search">` (needs `preventDefault`). `useMemo` around the flatten (≤1000 items, so not worth the noise).
- **Tradeoff accepted:** Older browsers without `<search>` lose the landmark, but the input still works. Search matches name, type and the Latin filler description, which is server behaviour: short queries like "a" match a lot.
- **With more time:** Show why a card matched (highlight the term).

## 11. Tinted type badges with measured contrast

- **Decision:** `TypeBadge` renders the type name in a tinted chip, `bg-X-500/20 text-X-300 ring-1 ring-X-500/30`, with one full literal class string per type. It replaces the starter's solid `bg-X-500 hover:…` map. Remapped: Fire red, Fighting orange (both were red), Rock stone, Normal neutral. Unknown types fall back to the Normal style.
- **Why:** I measured WCAG contrast from Tailwind's palette against the dark card: 13 of the starter's 18 white-on-solid pairs fail AA (as low as 1.44:1 for Ice). The tinted chips are all **≥ 7.26:1** (AAA). The type name is always written, so colour is never the only signal (WCAG 1.4.1). There's no hover style because badges aren't interactive. The class strings are literal because Tailwind only generates classes it finds in the source.
- **Alternative rejected:** Solid fills with per-type black or white text (18 pairs to hand-tune, and visually loud in a 5-column grid). Building class names dynamically (`bg-${c}-500`), which produces no CSS.
- **Tradeoff accepted:** Less saturated than classic Pokédex badges. The gray family (Normal, Rock, Steel, Dark) looks similar, and the label carries the meaning.
- **With more time:** Contrast checks in CI (e.g. axe in a Playwright test).

## 12. Resized images with a fallback chain

- **Decision:** `getCardImageUrl` rewrites the trailing `/<w>/<h>` of picsum and loremflickr URLs to `/400/500` (2× a ~200px column at 4:5). Other hosts and unparseable URLs pass through unchanged. `PokemonImage` tries the resized original, then on error `picsum.photos/seed/pokemon-<id>/400/500`, then on a second error a muted panel with the name's initial. The `<img>` has `alt=""`, `loading="lazy"`, `decoding="async"`, explicit `width`/`height` and `object-cover`, on a `bg-muted` background while loading.
- **Why:** The source images are up to ~4000px. I measured picsum at 393 KB / 1.9s for the original versus 18 KB / 0.26s resized. During development **loremflickr returned HTTP 500 for every image request** (half the dataset), even with a browser user agent, while its homepage loaded. The chain respects the data first (if loremflickr recovers, its images are used), degrades to a deterministic substitute (same id gives the same photo), and the last stage survives picsum being down too. `alt=""` because the photos are random stock images that don't depict the creature and the name is adjacent text, so describing them would add noise for screen-reader users. Explicit dimensions reserve space, so lazy images don't shift the layout.
- **Alternative rejected:** Placeholder only (half the grid would look broken). Rewriting every loremflickr URL to picsum up front (silently discards the data even after the host recovers). A descriptive alt (redundant or misleading).
- **Tradeoff accepted:** Each loremflickr card makes one fast failed request (~0.3s) before the swap. The resize depends on both hosts' URL formats. The backup photos are substitutes, not the data's images.
- **With more time:** Use `srcSet` with 1× and 2× sizes. Proxy images through the server with caching, so third-party outages are invisible.

## 13. `PokemonCard` flip implementation

- **Decision:** Both faces sit in one CSS grid cell (`[grid-area:1/1]`), so the card is as tall as its taller face. The inner wrapper rotates `rotateY(180deg)` with `preserve-3d` and `backface-visibility: hidden`, under `motion-safe:`. Under `motion-reduce:` nothing rotates and the hidden face fades to `opacity-0`. The hidden face is `inert`. One `<button type="button">` covers the card (`absolute inset-0`) with `aria-expanded`, `aria-controls` (pointing at the back, via `useId`) and `aria-label="<name> details"`. The front shows the image, the name as `<h2>` and the type badges. The back shows the name, a Legendary chip when it applies, the description (clamped to 3 lines), a `<dl>` of 6 stats (value as text plus a decorative `aria-hidden` bar scaled to 255), and a `<dl>` with height (m), weight (kg) to 1 decimal, and generation.
- **Why:** Grid stacking removes the need to guess a fixed height, so the back can never overflow. With the faces outside the button, the HTML stays valid (buttons can't contain headings or lists) and the button's name is "Devon details", not the whole stats block. Focus stays on the same button when flipping, so keyboard users never lose their place. `inert` removes the turned-away face from both the tab order and the accessibility tree, so exactly one `<h2>` per card is exposed. Stats are readable as text, with the bar as decoration. Abbreviations ("Sp. Atk", "Gen") have `sr-only` expansions. `cursor-pointer` is explicit because Tailwind v4's preflight resets buttons to the default cursor.
- **Alternative rejected:** Absolutely positioned faces with a fixed aspect ratio (a guessed height means overflow). The whole card as a `<button>` (invalid HTML, and a long accessible name). `aria-hidden` on the hidden face (doesn't stop focus). `<meter>` for stats (hard to style consistently across browsers).
- **Tradeoff accepted:** The units (m, kg) are an **assumption**: the data has none, but its ranges match real Pokémon. Text on the card can't be selected, because the overlay button covers it. The description is clamped visually (screen readers still get it all).
- **With more time:** Colour stat bars by value band. Add an Escape key to flip back. Visual regression tests for both faces.

## 14. Loading, empty, error and end states

- **Decision:** The first load shows 10 skeleton cards (two rows at 5 columns). The next page appends 5 skeletons. While a new search is loading, the previous results are dimmed with `aria-busy`. Empty: "No creatures match "x"." plus **Clear search**, which empties the input and focuses it. First-page error: a `role="alert"` block with **Try again** (`refetch`). Next-page error: an inline `role="alert"` under the loaded cards with **Try again** (`fetchNextPage`). End: the design's pill, "No more creatures found." An always-mounted `sr-only` `aria-live="polite"` paragraph announces "Loading creatures…", "N creatures found" or the error.
- **Why:** Every non-happy state either explains itself or offers the next action. Skeletons mirror the card's layout, so nothing jumps when data arrives, and appending them at the bottom keeps them where the user is looking. Live regions only announce changes to elements that already exist, so the region is never conditional. Placeholder data keeps the old count while searching, so screen readers hear one announcement per completed search, not one per keystroke. `role="alert"` is reserved for errors.
- **Alternative rejected:** A spinner (gives no layout preview). Replacing the grid on a next-page error (discards progress). A conditionally rendered live region (often silent). A shadcn `Button`, which would add `class-variance-authority` for three buttons, so a shared class string instead.
- **Tradeoff accepted:** The local API is near-instant, so skeletons and dimming are barely visible without an artificial delay. `pages[0].pagination.total` is assumed to be the same across pages (true for static data).
- **With more time:** Restore focus sensibly after a first-page retry. Use a shadcn `Button` if there were more buttons.

## 15. Dev-only latency and failure controls

- **Decision:** `server/devApiControls.ts` is Connect middleware mounted in `vite.config.ts`'s `configureServer`, before `app`. `?delay=<ms>` (capped at 5s) waits before responding. `?failFrom=<page>` returns 500 for that page and later ones. In dev builds, `fetchPokemonPage` forwards `delay` and `failFrom` from the page URL to the API.
- **Why:** The local API answers in ~4ms, so skeletons, dimming and both error states were impossible to see or demo. Mounting the middleware only in the Vite dev server makes it dev-only *by construction*: `server/index.ts` never loads it, and `import.meta.env.DEV` is statically false in production, so the forwarding code is removed (verified: `failFrom` is absent from both production bundles). The starter's `app.ts` is untouched. Real server latency (rather than a client `sleep`) means aborts behave as they would on a network. `failFrom` makes both the first-page and the next-page error demoable.
- **Alternative rejected:** Middleware in `app.ts` (edits the starter and ships to production). An `await sleep()` in `fetchPokemonPage` (fakes latency where aborts can't be observed). Browser devtools throttling (works, but can't force errors and is harder to show live).
- **Tradeoff accepted:** A small dev-only surface in `vite.config.ts` and `api.ts`. A forced failure stays failed on retry, so "Try again" can't be demoed succeeding without removing the parameter.
- **With more time:** A `failOnce` mode so retry can be shown succeeding. MSW (Mock Service Worker) for scripted scenarios in tests.

## 16. Fix the search input's non-text contrast in `ui/input.tsx`

- **Decision:** In the shadcn `Input`, the resting border is `border-foreground/40` (was `border-input`). On focus it's `border-foreground` plus a solid `ring-ring` (was `border-ring` + `ring-ring/50`). The fix lives in the component, with a comment explaining the divergence.
- **Why:** I measured every theme pairing. All text passes (≥ 6.91:1), as do the card and button focus rings (≥ 3.79:1), but the input failed WCAG 1.4.11: its border was **1.39:1** and its focus halo **1.83:1** against our pure-black page (shadcn's values were tuned for its lighter dark gray). Now: border **3.55:1**, focus border **20.11:1**, focus ring **4.44:1**. The boundary is how users find an empty field once the placeholder is gone. Using the `foreground` token instead of `white` keeps it theme-aware.
- **Alternative rejected:** A `className` override at the one call site, which keeps the shadcn file pristine but leaves the next input broken. Changing the global `--input` token, which also changes the input's background tint.
- **Tradeoff accepted:** `ui/input.tsx` now differs from upstream shadcn, so re-adding it with the CLI would overwrite the fix (the comment flags this).
- **With more time:** Automate contrast checks (axe or Playwright) so regressions like this are caught in CI.

## 17. Hint that cards are clickable: lift + flip icon

- **Decision:** On hover or keyboard focus (`has-[:focus-visible]`), the card lifts 4px (`motion-safe` only) and the overlay button shows a faint `ring-foreground/30` outline. A small flip icon (Lucide `rotate-cw`, inlined as SVG) sits in the front's top-right corner. It's always faintly visible (`text-white/70` on `bg-black/60`) and brightens on hover. The icon is `aria-hidden`.
- **Why:** A photo gives no cue that it's interactive. Touch screens have no hover (and Tailwind v4's `hover:` only applies on devices that can hover), so a hover-only hint would skip the users who need it most, which is why the icon is always visible. `focus-visible` instead of `focus-within`, so a mouse click doesn't leave the card lifted. The dark circle behind the icon keeps it legible over any random photo. The icon is decorative because the button's accessible name already says "details" and `aria-expanded` conveys the state.
- **Alternative rejected:** Lift only (no hint on touch). A peek-tilt on hover (more motion, still nothing on touch). `lucide-react` (a dependency for one icon).
- **Tradeoff accepted:** The icon covers a small corner of the photo.
- **With more time:** Briefly animate the icon on first visit, then never again.
